## 1. 基线：本次任务书依据的项目事实

### 1.1 项目定位

「安芯」是高校实验室安全**台账**系统：把试剂、柜位、规则、隐患串成一张可查、可算、可导出迎检的账。问答只是入口。

判据（来自可行性分析）：**删掉问答之后，如果什么都不剩，那它就是套壳。**本项目删掉问答，剩下的是台账、规则库、组合检查、隐患记录——所以成立。

### 1.2 P0 范围（本五天全部围绕这四项）

| 编号 | 功能 | 本五天做到什么程度 |
|---|---|---|
| P0-1 | 试剂台账 + 相容性组合检查 | 80 条试剂、10 组、25 对矩阵，柜级检查可用 |
| P0-2 | 规则库（可执行 + 可溯源） | 20 条规则，每条挂条款号 |
| P0-3 | 隐患记录与整改闭环 | 发现 → 记录 → 整改 → 复核，四态流转 |
| P0-4 | 本地化应急卡 | 静态页：处置步骤 + 本楼洗眼器 + 校医院电话 |

### 1.3 明确不做（谁提谁负责解释为什么）

① 纯知识问答（"硝酸有什么性质"）　② 通用实验操作指导　③ 任何"问一句答一句"的聊天形态　④ 校园二手/社交/资讯　⑤ 全自动视觉识别违规　⑥ 两千余种危化品全目录　⑦ 让大模型直接下安全结论

| 口径 | 速率 | 80 条耗时 | 用在哪 |
|---|---|---|---|
| 6 分钟/条 | 10 条/时 | 8.0 h | 可行性分析（保守基线，按 16 天窗口） |
| **4.5 分钟/条** | 13.3 条/时 | **6.0 h** | **本任务书（已有速查表）** |

> **红线**：若 D2 结束时实测速度慢于 4.5 分钟/条，**立即把目标从 80 条降为 60 条，不得靠加班补**。演示只需要"一个柜子装满高危试剂"，60 条足够撑起全部场景。

## 5. 数据契约 v1（D1 冻结，此后改动必须走 ADR）

> 契约即法律。任何字段增删，必须在 `docs/adr/` 写一条 ADR，并在交接文档中标注影响面。

### 5.1 命名与编码规范

- 所有 ID 使用 `前缀-序号`：试剂 `R-0001`、规则 `C-01`、矩阵对 `P-001`、柜子 `CAB-B3`、隐患 `F-YYYYMMDD-NNN`
- 存储组 ID 用大写英文短码：`OX` `FLAM` `ACID_IN` `ACID_ORG` `BASE` `WATER_REACT` `TOX` `HALA` `GAS` `OTHER`
- 所有 JSON 文件使用 **UTF-8 无 BOM**，两空格缩进，数组顶层元素顺序即展示顺序
- 任何字段不得为空字符串；未知填 `null` 并说明原因
- **无出处的规则不允许进入 `rules.json`**（`clause` 为必填且非空）

### 5.2 `reagents.json` — 试剂台账

```json
[
  {
    "id": "R-0001",
    "name": "硝酸",
    "aliases": ["浓硝酸", "HNO3"],
    "cas": "7697-37-2",
    "ghs": ["氧化性液体-类别3", "皮肤腐蚀-类别1A"],
    "storageGroup": "OX",
    "hazardNote": "强氧化性、强腐蚀；与有机物、还原剂、可燃物剧烈反应",
    "source": "《危险化学品目录》2015；GHS 分类",
    "verified": false
  }
]
```

| 字段 | 类型 | 必填 | 可空 | 说明 |
|---|---|---|---|---|
| `id` | string | ✔ | ✘ | `R-` + 4 位序号 |
| `name` | string | ✔ | ✘ | 中文正名，与标签一致 |
| `aliases` | string[] | ✔ | ✘ | 含俗名与分子式；无别名时为空数组 `[]` |
| `cas` | string | ✔ | ✔ | CAS 号，查不到填 `null` |
| `ghs` | string[] | ✔ | ✘ | GHS 危险类别，至少 1 条 |
| `storageGroup` | enum | ✔ | ✔ | 10 组之一；**填 `null` 表示"已入台账但尚未分类"**，该试剂不参与组对判定，进入 `unclassified` |
| `hazardNote` | string | ✔ | ✘ | 一句话危害描述 |
| `source` | string | ✔ | ✘ | 数据出处，供答辩追溯 |
| `verified` | boolean | ✔ | ✘ | 是否经第二人复核 |

> **关于 `storageGroup` 可空**：字段本身必填（必须存在），值允许为 `null`。校验脚本的要求是"键必须存在；非 `null` 时必须是附录 B 的 10 个组之一"。这样既有"未分类"这个真实状态，又不会让校验形同虚设。
>
> **注意**：示例里**没有 `formula` 字段**（分子式写进 `aliases` 即可）。若后续确实需要单独的分子式字段，走 ADR-001 增加，不要私自加。

### 5.3 `groups.json` — 存储相容组

```json
[
  {"id": "OX", "name": "氧化剂", "definition": "本身不燃烧但能放出氧、促进他物燃烧的物质", "examples": ["硝酸", "高锰酸钾", "过氧化氢"]}
]
```

### 5.4 `matrix.json` — 组间相容矩阵

```json
{
  "version": "1.0",
  "updated": "2026-11-10",
  "pairs": [
    {
      "id": "P-001",
      "a": "OX",
      "b": "FLAM",
      "verdict": "forbidden",
      "reason": "氧化剂与易燃物混存会加速氧化放热，可能自燃或爆炸",
      "clause": "教育部《高等学校实验室安全检查项目表》化学安全 6.2.3",
      "ref": "GB 15603-2022 第 5.3 条"
    }
  ]
}
```

`verdict` 枚举：`forbidden`（红）/ `caution`（黄）/ `compatible`（绿）。

**矩阵是无向的，写入时按固定组序去重**：约定的组序 = **附录 B 表格中从上到下的行序**（`OX` < `FLAM` < `ACID_IN` < … < `OTHER`），写入时 `a` 必须排在 `b` 之前。校验脚本按此顺序检查，`(OX,FLAM)` 与 `(FLAM,OX)` 同时出现即报错重复对。

> **示例中的条款号是占位，不是真实出处。** `clause` 与 `ref` 两个字段在 D1 阶段一律先填 `"TODO-占位"`，必须在 D2 结束前用 `data/checklist.xlsx`（T1.10 产出）逐条核对替换。**带 TODO 的记录不得进入 D3 的 G1 抽查**——编造条款比留空危险得多（AGENTS.md §10 规则 6）。

### 5.5 `rules.json` — 规则库

```json
[
  {
    "id": "C-01",
    "name": "氧化剂与易燃物同柜",
    "scope": "cabinet",
    "trigger": {"type": "groupPair", "a": "OX", "b": "FLAM"},
    "effect": {"level": "red", "title": "柜内同时存在氧化剂与易燃物"},
    "advice": "将氧化剂移出本柜，或改为物理隔离存放",
    "clause": "教育部《高等学校实验室安全检查项目表》化学安全 6.2.3",
    "enabled": true
  }
]
```

`trigger.type` 本版只支持三种：

| type | 参数 | 含义 |
|---|---|---|
| `groupPair` | `a`, `b` | 两存储组同柜 |
| `reagentPair` | `a`, `b` | 两个具体试剂同柜（特例，优先级高于组级） |
| `itemMissing` | `field` | 试剂缺必填字段（如 `storageGroup` 为空） |

**matrix 与 rules 的分工（重要，不要混）**

| 文件 | 是什么 | 谁维护 | 能不能直接产生结论 |
|---|---|---|---|
| `matrix.json` | 化学事实："哪些组不能同柜" | C（数据） | **不能**。它只陈述事实，不含级别与建议 |
| `rules.json` | 检查逻辑："引擎跑哪些检查、违反报什么级别、给什么建议" | C 起草 / **B 审核合入** | **能**。所有 `conflicts` 必须由规则产生 |

> **引擎不得直接读矩阵下结论**，必须经由规则。否则同一条化学事实会在两处被重复实现，改一处漏一处。
> `rule.trigger` 通过 `a`/`b` 引用矩阵中的组；`reagentPair` 特例则不查矩阵，直接生效。
>
> **起草与合入分离**：10 条特例规则由 C 起草（化学知识更熟），但必须经 B 审核后合入 `rules.json`。理由：规则要同时满足"化学上对"和"引擎能跑"，单人容易只满足一半。G1 抽查时责任归 B。

### 6.1 `checkCabinet(cabinet, dataset)`

```js
// 入参
//   cabinet: 单个柜子对象（结构见 §5.6）
//   dataset: { reagents, groups, matrix, rules }  —— 均为已解析的数组
// 由调用方负责装载：小程序从打包进工程的 JSON require；单测直接 require 文件

// 出参
{
  "cabinetId": "CAB-B3",
  "level": "red",                 // red | yellow | green | unknown
  "confidence": "high",           // high | medium | refuse（聚合规则见 6.3）
  "conflicts": [
    {
      "ruleId": "C-01",
      "level": "red",             // red | yellow
      "confidence": "medium",     // high（特例命中）| medium（组级命中）
      "title": "柜内同时存在氧化剂与易燃物",
      "a": {"reagentId": "R-0001", "name": "硝酸"},
      "b": {"reagentId": "R-0011", "name": "乙醇"},
      "clause": "教育部……（占位，待核对）",
      "advice": "将氧化剂移出本柜，或改为物理隔离存放"
    }
  ],
  "uncoveredPairs": [
    {"a": "TOX", "b": "HALA", "note": "该组对未收录，需专业人员确认"}
  ],
  "unclassified": [
    {"reagentId": "R-0042", "name": "某未分类试剂"}
  ]
```


| 档位 | 条件 | UI |
|---|---|---|
| `high` | 按 `name` 或 `aliases` **精确命中且只命中一条** | 直接展示卡片 |
| `medium` | 命中多条（让用户选），或仅"包含"匹配 | 列出候选，提示"请确认是哪一个" |
| `refuse` | 无任何命中 | "未收录，请手动录入或询问安全员" |

### 6.3 置信度：**先定逐对，再聚合成柜**（这是本项目的技术卖点，必须严格实现）

置信度有**两级**：每个组对/冲突各自有一个档位，柜子的 `confidence` 是对它们的**聚合**——不是"整体印象"，也不是独立判断。

#### （1）逐对档位（pair-level）

| 档位 | 触发条件 | UI 表现 |
|---|---|---|
| `high` | 命中 `reagentPair` **特例规则**（针对具体两种物质），且 `clause` 非空 | 红/黄 + 条款号 +「特定组合」标记 |
| `medium` | 命中 `groupPair` **组级规则**（引用矩阵中的 pair），且 `clause` 非空 | 红/黄 + 条款号 +「类别级判定，建议复核」标记 |
| `uncovered` | 该组对既无特例、也无组级规则（矩阵未覆盖） | **不下结论**，列入 `uncoveredPairs`，提示"需专业人员确认" |
| `unclassified` | 试剂 `storageGroup` 为 `null` | 该试剂不参与任何判定，列入 `unclassified` |

**为什么组级只能给 `medium`**：组级规则的依据是"氧化剂类不能与易燃类同柜"这种**类别级**判断，对具体这一对物质未必都成立。把它标成 `high` 是在撒谎。真正能担保具体组合的只有 `reagentPair` 特例——所以我们专门写了 10 条特例，**这正是它存在的理由**。

> 答辩话术：「同一柜子里，特例级判定我们给高置信，类别级判定我们会明确告诉用户'建议复核'，覆盖不到的直接说不知道。这是刻意设计的不确定度，不是能力不足。」

#### （2）柜级聚合（规则写死，不许临场发挥）

```
第一步  refuse 判定
        若 柜内试剂数为 0，或 全部试剂 storageGroup 为 null
        → confidence = "refuse"，level = "unknown"，直接返回

第二步  逐对判定
        对柜内每种试剂取 storageGroup；
        null 的进 unclassified，不参与两两判定；
        非 null 的两两组合，按 6.4 的优先级查规则，产出 conflicts / uncoveredPairs

第三步  confidence 聚合
        候选 = 所有命中的冲突的档位
        若 uncoveredPairs 非空 或 unclassified 非空 → 整体封顶为 "medium"
        否则 → 取 min(候选)，即 high 与 medium 混在一起时按 medium 算
        （无任何命中且无缺口时，confidence = "high"）

第四步  level 聚合
        存在 red 冲突                          → "red"
        无 red，但存在 uncovered/unclassified   → "unknown"
        无 red/无缺口，但存在 yellow 冲突        → "yellow"
        其余                                    → "green"
```

**关键点**：`uncovered` 与 `unclassified` **只降级、不拒答**。部分没覆盖，不影响已覆盖部分的结论照常输出——否则 10 个组 45 个组对、矩阵只覆盖 25 对，任何一个真实柜子都会因为一对未覆盖而整柜变灰，G2 的"选柜 → 看到红色冲突"当场失败。

**实现约束**：置信度**只能来自规则覆盖度**，不得来自任何模型自评分。这条写进代码注释与答辩稿。

### 6.4 判定优先级

```
reagentPair 特例（high）  >  groupPair 组级规则（medium）  >  无规则（uncovered，不下结论）
```

柜内两两组合共 C(n,2) 对。**特例优先于组级**：若同一对试剂既命中特例又命中组级规则，只输出特例那一条（档位 `high`），避免同一问题报两次。

## 9. 交接文档机制（硬性规则）

### 9.1 触发时机

| 场景 | 是否必须写交接 |
|---|---|
| 每个开发日结束（D1–D5） | **必须** |
| 任一闸门判定后（G1/G2） | **必须** |
| 任何一次向 GitHub 推送前 | 必须更新 `handovers/INDEX.md` |
| 契约变更（ADR） | 必须，且同步更新 `docs/data-contract.md` |
| 人员轮换/请假超过 1 天 | **必须**（写"当前断点"） |

### 9.2 强制内容（缺一项视为未完成）

1. **一句话结论**：能不能进入下一阶段
2. **完成项**：对照任务书 ID 逐条打勾，附证据（文件路径 / commit SHA）
3. **未完成项**：原因 + 新的预计完成时间
4. **决策记录**：本阶段改了什么契约，为什么，影响谁
5. **踩坑记录**：现象 → 原因 → 解决办法（给下一个人省时间）
6. **变更清单**：动了哪些文件、哪些数据
7. **下一阶段入口条件**：满足什么才能开工
8. **风险更新**：新增/关闭的风险编号
9. **待回答的问题**：需要谁、在什么时候、回答什么

### 9.3 文件命名与索引

- 日交接：`handovers/D1.md` … `handovers/D5.md`
- 闸门交接：`handovers/G1.md`、`handovers/G2.md`
- 索引：`handovers/INDEX.md` 一行一条，格式 `| 日期 | 阶段 | 结论 | Commit |`

> **没有交接文档的阶段 = 没做完。**下一个接手的人（或 AI）只能靠这份文档，不靠记忆。

## 10. 协作与 Git 规范

### 10.1 分支

- `main` 永远可运行，任何人 clone 后能跑通 §4.3 的三条命令
- 功能分支：`feat/d3-cabinet-check`、`fix/d5-export-crash`
- 合并前必须：单测通过 + 至少 1 人看过 diff

### 10.2 提交信息

```
<type>(<scope>): <中文描述>

type  : feat | fix | data | docs | chore | refactor | test
scope : mp | engine | data | docs | infra
```

示例：
- `feat(engine): 支持组对判定与条款溯源`
- `data: 补充 15 条试剂至 80 条`
- `docs: D3 交接文档`

### 10.3 提交纪律

- 一个 commit 只做一件事
- 数据变更单独提交，前缀 `data:`
- 禁止 `git push --force` 到 `main`
- 单文件 > 5 MB 不进仓库

### 10.4 网络（Clash Verge）

本机代理：`http://127.0.0.1:7897`

```powershell
# 方式一：仅本次会话
$env:HTTP_PROXY="http://127.0.0.1:7897"; $env:HTTPS_PROXY="http://127.0.0.1:7897"
git push origin main

# 方式二：写入本仓库配置（推荐，不影响其他项目）
git config --local http.proxy http://127.0.0.1:7897
git config --local https.proxy http://127.0.0.1:7897
```

### 10.5 每日站会（10 分钟，线上即可）

三个问题：昨天做完了什么 / 今天要做什么 / 有什么卡住。
站会结论**必须**落进当日交接文档。

## 附录 C　术语

| 术语 | 含义 |
|---|---|
| 存储组 | 化学品的存储相容类别，同组默认可同柜 |
| 组对判定 | 两个存储组能否同柜的结论（forbidden / caution / compatible） |
| 特例规则 | 优先于组对的、针对具体两种试剂的规定 |
| 条款号 | 规则依据的具体条文编号，必须可追溯 |
| 逐对档位 | 单个组对判定的置信度（high / medium / uncovered / unclassified） |
| 柜级置信度 | 由逐对档位聚合而来，规则见 §6.3，不是独立判断 |
| fixture | 每条规则的最小触发样例，放 `engine/test/fixtures/`，G1 靠它验 |
| refuse | 柜级无法给出任何结论的状态（空柜 / 全部未分类），不是错误 |
| 闸门 | 到点必须通过的硬判据，不通过即降级 |
